# Surface RT display appliance

The Surface runs a read-only OS with SSH, OpenTegra Xorg, and a display receiver started by the PC. The proven base can boot through APX and RAM U-Boot or the tested USB EFI chain. The owner reports successful Power-only internal EFI boot after installing release `4864cffb6f74e79c22c52c17`. Pinned SSH confirms that release in `/proc/cmdline`. The kernel includes the tegra_vde cache-sync patch. Nura on p2 remains untouched.

## Decisions

| Area | Choice | Why |
|---|---|---|
| Userspace source | Alpine edge armv7 binary APKs, version-locked in `packages.lock`. The `.apk` files are archived under `cache/apks/` and checked by sha256. | GStreamer 1.28.7 is the exact version proven on this device; v3.24 ships 1.28.3. Rebuilding userspace from source would add work without changing what boots. |
| Init | OpenRC + eudev, Alpine's default | The packages are built for it. No logind, no session manager. The receiver needs neither. |
| Rootfs | A full `rootfs.squashfs`, or one checked `extension.squashfs` above frozen base `6258b2a5368a`, with a tmpfs writable layer | The extension fits the available boot partition without deleting the base. Both lower layers are read-only. No recursive release inheritance or p2 writes. |
| Kernel | Pinned tarball `bfffc6d` plus the patch. Config identical to the running kernel. VDE stays `=m`, enabled with `tegra_vde.skip_capture_cache_sync=1` on the cmdline. | The smallest delta from the proven kernel. In-tree modules are signed by the same build, so there is no taint. |
| Identity | The existing SSH host keys and `authorized_keys` are copied once into `p1:/appliance/identity/` by the user-run installer. | The pinned host key keeps working. The appliance never generates keys. |
| Boot selection | RAM U-Boot uses the extlinux `DEFAULT`; internal EFI uses its generated `startup.nsh` and namespaced payloads | `surface-boot-select` does not change EFI startup. PC UMS backup and restore cover overwritten EFI files separately. |
| Sender | Unchanged | It already passes `DISPLAY=:0 XDG_RUNTIME_DIR=/run/user/10000` and the receiver path. |
| Power policy | `surface-idle` owns button gestures, manual backlight intent, confirmation, and appliance DPMS | Short release toggles illumination. A 3-second hold requests a visible 30-second countdown. A fresh Power press cancels. |
| Presentation ownership | Appliance receivers acquire a private local lease before constructing their Xv presenter | Confirmation revokes the lease, waits for cleanup, and excludes the hardware overlay before starting its countdown. Cancellation uses the sender's existing reconnect path. Visible ACKs remain tied to real presentation. |

## Layout

```text
PC: appliance/
  build.sh               one entry point: kernel → rootfs → initramfs → release
  build-kernel.sh        pinned tarball + patch → out/kernel/{zImage,dtb,kernel.release,config,modules/}
  build-rootfs.sh        Docker alpine:edge, apk --arch armv7 --root, proot+qemu-arm for scripts → out/rootfs.squashfs
  build-initramfs.sh     busybox-static + storage modules + init → out/initramfs
  build-internal-efi.py  existing overlay + frozen base + proven EFI payloads → extension bundle
  packages.txt           world list (hand-edited)
  packages.lock          name version sha256 (generated by lock.sh, reviewed)
  overlay/               files copied into the rootfs (OpenRC services, sshd_config, xorg.conf, doas rule)
  install/               surface-install.sh stages native releases; internal-efi-pc.py inspects, installs, and restores EFI bundles through PC UMS

Release: ~/surface-releases/<id>/
  zImage  initramfs  tegra30-microsoft-surface-rt.dtb  rootfs.squashfs  manifest.json  SHA256SUMS

Device p1 (FAT, 17C0-8631):
  /vmlinuz /initramfs /dtbs/...          Nura, untouched
  /extlinux/extlinux.conf                Nura label + one label per release
  /appliance/<id>/...                    release files
  /appliance/identity/                   ssh_host_*_key{,.pub}, authorized_keys
  /appliance/<efi-id>/extension.squashfs checked extension above the frozen base
  /appliance/<efi-id>/release.conf       base and extension identities
  /EFI/BOOT/... /EFI/Microsoft/Boot/...  candidate boot chain, backed up before activation
  /startup.nsh                          internal-only marker scan and namespaced EFI launch
  /appliance/recovery/extlinux.conf.orig original config, byte-exact
```

## Internal EFI and Power acceptance

The extension builder reuses packages and modules from the immutable base. The new initramfs verifies its bound descriptor and both SquashFS hashes before mounting `lowerdir=/ro_extension:/ro_base` with RAM upper and work directories. The original full-image boot format remains a supported recovery path.

The PC installer verifies the bundle, USB transport, FAT UUID and mount association, base hash, protected Nura files, and peak free-space demand. It saves affected files and original absences to a verified host-side receipt before overwriting anything. Dependencies precede startup and WBM activation. Restore reconciles interrupted operations against recorded hashes and refuses unknown changes. Multi-file FAT activation is recoverable, not atomic against power loss.

### EFI handoff and observed boot

The internal chain uses Windows Boot Manager, the retained BootShim, the OpenRT ARM EFI shell, and generated `startup.nsh`. The script finds the internal volume through `surface-appliance-internal.id`, then loads the namespaced `zImage`, `initramfs`, and EFI-specific device tree. It preserves `efi=noruntime`. Extlinux is not part of this startup path.

`build-internal-efi.py` verifies the retained chain against `nura/coldboot/nv-efi-kernel-probe/manifest.json` before packaging it. Keep those exact source artifacts and their hashes. That manifest records the earlier kernel packaging probe, including its original verification limits. Later physical observations belong in `nura/coldboot/decisions.tsv`, not in the frozen source manifest.

After the owner-run installation, the owner reports that startup reaches the display but takes more than five minutes from the Power press. This is an estimate, not an instrumented duration. Pinned SSH reads `appliance.release=4864cffb6f74e79c22c52c17` and the namespaced EFI payload paths. That confirms the running release, not the duration of each boot stage. The delay has not been attributed to firmware, EFI loading, Linux initialization, or network connection.

### Shutdown confirmation

The runtime does not infer confirmation visibility from an X11 window alone. It closes receiver admission, revokes existing leases, waits for presenter cleanup, reserves the Xv port, and checks backlight, scanout, rendering, and vblank progress. A failed witness aborts shutdown. Only a counting state has a shutdown deadline.

Local state, socket, UI, and installer checks do not prove Tegra hardware behavior. Physical acceptance includes Power-only boot without rescue USB, visible countdown while streaming, consumed initiating release, fresh-press cancellation, manual-off restoration, network continuity, clean shutdown, and another cold boot. See [Install internal EFI](../docs/install.md#install-internal-efi).


## Units

Riskiest first. Each unit ends in a check.

1. **Kernel lever.**
   - Check: the effective config is identical to the running config, and the patch applies with no fuzz.
   - Check: module `.text` matches stock except tegra-vde and 3 known modules.
2. **Rootfs lever.**
   - Check: under qemu, `python3 -c 'import gi; Gst...'` loads.
   - Check: `gst-inspect-1.0 v4l2slh264dec` is present, and `Xorg -version` runs.
   - Check: the package versions equal the lock.
3. **Initramfs and release bundle.**
   - Check: the cpio contents include every needed module for `kernel.release`.
   - Check: the init script passes `sh -n`, and the manifest hashes verify.
4. **Stage (user sudo on Nura).**
   - Steps: the release goes to `p1:/appliance/<id>`, the label is added, and the identity is captured. DEFAULT stays `surface-rt`.
   - Check: the bundle `sha256sum -c` passes before any sudo, and the Nura boot files hash the same before and after.
5. **Recovery rehearsal, then select (user, APX).**
   - UMS (`ums 0 mmc 0`) exposes the whole eMMC to the PC writable. Only p1 is touched, through `recovery-pc.sh`, which mounts it with udisks (no sudo).
   - Steps: APX → Volume Down → bootmenu → "mount internal storage". On the PC, run `recovery-pc.sh status`, then `recovery-pc.sh select <id>`. This exercises the same write path as `restore`. Exit UMS, then "boot Linux from internal storage".
   - If any of those steps fails, nothing has changed: DEFAULT is still Nura.
   - Also note whether the extlinux menu responds to the buttons.
6. **Boot the appliance.**
   - Check: `verify-boot.sh <id>`, i.e. the cmdline, `skip_capture_cache_sync=Y`, `tainted=0`, the root is overlay, p2 is not mounted, and no desktop processes are running.
   - Check: the pinned host key is accepted.
   - If it fails: APX → UMS → `recovery-pc.sh restore` → Nura.
7. **Stream gates.**
   - Production `surface-display.service` works unchanged.
   - Checksum equals stock, replay ×5 (decoder p50 ≤ 20.5 ms), and live cadence matches or beats the Nura result.
8. **Durability.**
   - A second APX boot passes the unit 6 checks without any manual step.
   - `surface-boot-select nura` brings Nura back.
